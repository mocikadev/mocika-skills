# arch-guard

让 AI 在写代码时持续考虑职责边界、模块拆分、依赖方向和后续演进，而不是只追求“这次能运行”。

## 解决什么问题

AI 编码常见两个极端：不断把业务、UI、数据库和网络逻辑堆进同一个文件；或者为了表现“架构能力”，机械套用分层、设计模式、多 crate 和微服务。两者都会增加理解、测试和修改成本。

`arch-guard` 使用风险分级和多层级边界判断，在不扩大无关重构范围的前提下约束代码结构。它关注的不只是文件，还包括函数、类型、模块、package、Rust crate、workspace、子系统和服务。

## 提供哪些能力

### 变更分级

- **L0 机械变更**：快速检查后直接执行。
- **L1 局部变更**：确认职责归属和依赖方向后执行。
- **L2 结构性变更**：编码前输出简短架构摘要。
- **L3 架构级变更**：比较方案、设计迁移与验证，并在实施前等待确认。

### 多层级职责治理

- 根据职责、变化原因、依赖和生命周期选择拆分层级。
- 识别巨型函数、文件、模块，以及尚未超行数但已经职责混乱的单元。
- 评估 Rust crate/workspace、Java/Gradle module、TypeScript workspace、Go package/module、C# project 等工程边界。
- 定义最小公共接口、状态所有权、错误语义和测试边界。

### 双向防护

- 防止为了少改文件继续堆积代码。
- 防止只按行数切割、创建 `utils/helpers/common` 垃圾桶。
- 防止滥用设计模式、无价值接口和假想扩展点。
- 使用童子军原则局部改善旧代码，不借小需求发动大重构。

### 实现后验收

检查职责、边界、依赖与数据流、扩展性、可测试性及设计一致性，并要求用实际测试和静态检查结果支持完成结论。

## 输入与输出

输入可以是新增功能、缺陷修复、重构请求、架构评审，或对现有代码的直接修改任务。L0 只做轻量结构核对；L1–L3 会读取项目规则、构建清单、目录、目标代码和相邻模块。

根据等级输出：

- L0/L1：简短结构判断和实现结果。
- L2：职责、模块归属、依赖、数据流、拆分决定与测试边界摘要。
- L3：2–3 个方案、推荐理由、公共契约、迁移/回滚策略和确认门禁。
- 完成后：架构结果与验证证据。

## 产物示例

```markdown
架构判断：
- 变更等级：L2
- 当前职责：app.rs 负责 UI 状态和事件
- 新增职责：OAuth、重试和离线队列
- 模块归属：新增 sync 模块；app.rs 只保留触发和状态展示
- 依赖与数据流：UI → 同步用例 → HTTP/队列实现
- 拆分决定：保持单 crate，暂不拆 workspace
- 测试边界：独立验证重试、队列恢复和状态转换
- 主要取舍：增加一个明确模块，避免完整架构迁移
```

## 安装与使用

```bash
skm install mocikadev/mocika-skills:arch-guard --link-to all
```

安装后可直接提出编码任务，也可以显式触发：

- `使用 arch-guard 实现这个新功能。`
- `别继续往这个 Rust 文件堆代码，检查是否该拆 module 或 crate。`
- `评估这次跨模块修改的职责边界和依赖方向。`
- `审查当前实现有没有过度设计或架构退化。`

## 与其他规则的关系

- 项目的 `AGENTS.md`、设计文档和既有架构决策优先。
- `project-ai-system` 负责项目级 AI 工作系统；`arch-guard` 负责具体代码变更的架构质量。
- Rust、Android、GNOME 等专项 Skill 负责语言和框架细节；`arch-guard` 提供通用的边界与依赖决策方法。
- Skill 不替代项目调查，也不会强制所有项目采用同一种分层结构。

## 维护与验证

修改 Skill 规则后，使用 [`references/validation-scenarios.md`](./references/validation-scenarios.md) 进行无 Skill 基线与加载 Skill 后的压力场景对照，重点检查是否同时阻止代码堆积和过度拆分。
