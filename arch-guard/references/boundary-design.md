# 职责与边界设计

## 四步判断法

### 1. 写出职责句

用一句话描述每个候选单元：

> 负责 `<能力>`，不负责 `<外围职责>`。

若一句话必须列出多个无关动作，先拆出职责清单。不要以一次需求、一个页面或一个工单名称代替长期职责。

### 2. 找出变化原因

标记代码因什么而变化：

- 产品规则和业务不变量
- 用例流程和状态转换
- UI、HTTP、CLI 等交互协议
- 数据库、文件、网络和第三方服务
- 序列化、传输对象和兼容协议
- 运维配置、日志和观测

不同变化原因不必一律分包，但必须有清晰边界；稳定核心不应依赖易变外围。

### 3. 选择最小有效层级

| 层级 | 适合形成边界的信号 |
|---|---|
| 函数 | 独立算法或处理阶段，无独立状态所有权 |
| 类型 | 拥有状态、不变量或明确行为 |
| 文件 | 围绕一个主要概念组织实现 |
| 模块 | 一组高内聚职责，需要隐藏内部实现 |
| package/crate/project | 需要公共 API、依赖隔离、独立测试或构建边界 |
| 子系统/服务 | 需要独立运行、发布、扩缩容或故障隔离 |

优先选择能真实隔离变化的最低层级。拆到更高层级必须有额外收益，而不仅是目录更整齐。

对 L2 新能力，先判断现有内聚模块能否自然承载。若新增职责具有独立变化原因，再建立一个按业务能力命名的模块。只有某部分拥有独立状态所有权、外部依赖、生命周期、错误语义或测试边界时，才从模块内部继续拆文件；不要在尚未读到实现前预先画出完整目录树。

### 4. 定义边界契约

每个新边界必须回答：

- 对外提供哪些能力？
- 输入、输出和错误语义是什么？
- 哪些类型必须公开，哪些保持私有？
- 谁拥有状态，谁可以改变它？
- 允许依赖哪些上游和下游？
- 如何独立测试或替换实现？

答不清时，边界尚未形成。

## 依赖与数据流

- 存在稳定业务规则时，让易变实现依赖该规则定义的最小边界；没有独立业务规则或替换需求时可以直接组合具体类型。
- UI/接口负责输入输出映射，不承载核心规则。
- 只有独立测试、替换或演进收益明确时，才由业务侧定义基础设施契约；否则不要为固定实现强造接口。
- 状态只有一个明确所有者；跨边界传递命令、结果或不可变快照。
- 错误在边界处转换为该层能表达和处理的语义。
- 循环依赖是边界错误信号，不能用全局状态或回调链掩盖。

## 拆分信号

- 一个单元出现多个独立变化原因。
- 新功能需要理解大量无关代码才能修改。
- 公共接口不断加入只服务于某个调用方的方法。
- 测试必须启动 UI、数据库或网络才能验证核心规则。
- 两部分具有不同依赖、生命周期、发布频率或故障模式。
- 新增行为总靠复制分支或修改中心调度器完成。

## 保留聚合的信号

- 代码共同维护同一个不变量，拆开会制造双向协作。
- 只有一个真实用例，抽象没有可替换对象。
- 拆分后主要是转发调用，没有减少依赖或隐藏细节。
- 边界会迫使大量内部类型公开。
- 规模来自声明、生成内容或紧密相关的规则表，而非职责混合。

## 防止伪拆分

禁止：

- 按固定行数平均切文件。
- 创建无法描述领域含义的 `utils`、`helpers`、`common` 容器。
- 每个函数一个文件，导致一次行为跨越大量跳转。
- 用接口包住永远只有一个简单实现的类型。
- 用 repository、factory、event bus 或依赖注入容器替代边界思考。
- 只移动代码，不收紧可见性、依赖和状态所有权。
- 未读取构建清单就假设项目需要新的库、框架或运行时。

## 设计模式采用条件

模式必须对应已观察到的问题：

| 模式 | 合理信号 |
|---|---|
| Strategy | 存在两个以上可替换行为，调用方不应知道具体实现 |
| Adapter | 外部接口不稳定或其类型不应进入核心 |
| Repository | 业务用例需要独立于存储语义进行测试和演进 |
| State | 状态转换具有明确规则，分支已难以保证合法转换 |
| Observer/Event | 确有一对多通知且发送方不应依赖接收方 |
| Factory | 创建过程复杂、依赖组合多或必须隔离具体类型 |

简单函数、组合、枚举或具体类型足够时，不采用模式。
