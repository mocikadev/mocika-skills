# 变更分级与门禁

按影响范围、边界变化和失败风险综合判断，不按文件数量机械分级。无法确定时取较高等级。

## 快速判定

| 等级 | 典型情况 | 编码前要求 | 用户门禁 |
|---|---|---|---|
| L0 机械变更 | 文案、格式、明确配置值 | 快速确认不改变结构 | 无 |
| L1 局部变更 | 单一职责内的缺陷或同类行为 | 检查归属、依赖与单元健康度 | 无 |
| L2 结构性变更 | 新业务能力、外部依赖、跨模块数据流、局部拆分 | 输出架构摘要 | 有明显不同方案时确认 |
| L3 架构级变更 | package/crate/服务拆分、核心依赖反转、公共模型迁移 | 方案比较、迁移与验证设计 | 实施前强制确认 |

## 自动升级信号

出现任一情况至少为 L2：

- 引入新的业务概念或变化原因。
- 跨越已有模块或层级边界。
- 引入数据库、网络、文件系统、消息系统或第三方 SDK。
- 需要扩大公共接口、共享可变状态或添加反向调用。
- 目标单元已职责过载，新增代码会继续恶化。
- 出现重复分支、全局状态、循环依赖或协议细节泄漏。

出现任一情况通常为 L3：

- 新建、合并或拆分 package、crate、workspace member、进程或服务。
- 改变核心公共 API、持久化模型或跨系统协议。
- 调整主要依赖方向、状态所有权、并发模型或部署边界。
- 需要分阶段迁移、兼容旧行为或设计回滚方案。
- 影响多个领域模块，失败会造成数据、安全或兼容性风险。

文件数量少不构成降级理由；一次修改也可能改变系统边界。

## L1 快速检查

实施前确认：

- 新代码属于目标单元现有职责。
- 没有新增依赖方向或泄漏实现细节。
- 不会继续扩大已经过载的文件、类型或模块。
- 更小的直接实现足以满足需求。

任一项无法确认，升级到 L2。

## L2 架构摘要

使用以下短格式，禁止用“提高扩展性”“降低耦合”等空话代替证据：

```markdown
架构判断：
- 变更等级：L2
- 当前职责：
- 新增职责：
- 模块归属与边界：
- 依赖、状态与数据流：
- 拆分或保留决定：
- 测试边界：
- 主要取舍：
```

若只有一个符合现有架构的明显方案，可说明后继续。若方案会导致不同公共接口、依赖方向或迁移成本，先让用户选择。

## L3 方案要求

实施前必须给出：

1. 当前结构、问题证据和目标。
2. 明确非目标，限制重构范围。
3. 2–3 个可行方案及成本、收益和风险。
4. 推荐方案与拒绝其他方案的理由。
5. 模块、package/crate、子系统或服务边界。
6. 公共接口、依赖方向、状态所有权、数据流和错误传播。
7. 兼容、迁移、回滚和测试方案。

获得用户明确确认后实施。确认只覆盖已展示的方案；实现中若改变核心边界、公共契约或迁移策略，必须重新确认。

## 降级与例外

- 项目已有明确方案且本次只是按方案施工，可以降低说明篇幅，不能跳过边界核对。
- 自动生成文件、声明数据等规模较大但没有多重职责时，可豁免规模预警。
- 用户明确要求只分析时，输出判断和建议，不实施。
- 用户要求赶时间时，缩小方案范围、减少非必要抽象；不得把新职责直接塞进错误边界。
