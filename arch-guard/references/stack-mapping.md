# 技术栈结构映射

先读取构建清单和现有目录，再使用本表识别候选边界。项目规则、框架惯例和专项 Skill 优先；不要照表重建项目。

## Rust

| 层级 | 载体 | 判断重点 |
|---|---|---|
| 文件内 | 函数、类型、私有 `mod` | 状态与不变量是否独立 |
| 模块 | `mod`、目录模块 | 可见性、错误语义、循环依赖 |
| 包边界 | crate | 公共 API、feature、依赖隔离、编译与测试成本 |
| 工作区 | workspace member | 多个 crate 是否共同发布、是否真有独立演进需求 |

不要看到核心/基础设施就自动拆 crate。只有依赖隔离、独立复用/测试、编译边界或多应用共享等收益足够时才提升。优先使用 `pub(crate)` 和私有模块收紧接口。

## Java / Kotlin

- 类和文件承载单一概念；package 表达稳定职责，而非只按 controller/service/repository 技术层堆放。
- Gradle/Maven module 用于依赖、构建、发布或团队边界；不要仅为目录整洁拆子项目。
- 检查跨 package 可见性、依赖反转和 DTO/实体泄漏。

## TypeScript / JavaScript

- 文件与目录模块围绕能力组织，避免万能 `index.ts`、`utils.ts` 和跨域 barrel export。
- package 或 monorepo workspace 适用于独立依赖、构建、发布或多应用共享。
- 检查运行时边界、循环 import、前后端协议类型和副作用初始化。

## Python

- 函数、类、module、package 依次形成边界；不要用单个 `helpers.py` 收容无关逻辑。
- distribution 仅在需要独立安装、发布或依赖管理时采用。
- 检查导入副作用、循环 import、隐式全局状态和框架对象向领域逻辑泄漏。

## Go

- package 是主要封装边界；从调用方需求定义小接口，不创建 `util`、`common` 包。
- Go module 用于版本和依赖边界，不等同于普通 package 拆分。
- 检查 `internal/` 使用、包循环、共享可变状态和过大的中心 package。

## C#

- 类型与 namespace 表达概念组织；project/assembly 提供依赖、构建和发布边界。
- solution 只是工程聚合，不代表运行时架构。
- 检查领域项目是否反向依赖 UI、ORM 或具体基础设施项目。

## 跨进程与服务

只有出现以下需求时才考虑进程或服务边界：

- 独立部署、扩缩容或故障隔离。
- 明确的安全、合规或数据所有权边界。
- 不同运行时、资源模型或发布节奏。
- 团队边界稳定，并能承担协议与运维成本。

如果只是代码职责不同，优先使用同进程模块或包。服务拆分会新增网络失败、数据一致性、观测、版本兼容和部署成本，必须在 L3 方案中明确说明。

## 通用检查

无论技术栈，确认：

1. 边界承载真实职责，而非映射文件夹偏好。
2. 对外接口小于内部能力，具体实现保持隐藏。
3. 依赖方向可从构建清单和 import/use 关系解释。
4. 存在独立核心规则时，可以在不启动外围系统时验证；没有核心规则的简单流程不强行分层。
5. 提升层级带来的收益大于 API、构建和维护成本。
