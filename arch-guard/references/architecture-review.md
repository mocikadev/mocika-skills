# 实现守卫与架构验收

## 实现过程中

每完成一个结构单元后检查：

- 新代码仍在已确定的职责范围内。
- 没有为了方便访问而扩大公共接口或可见性。
- 没有出现跨层调用、反向依赖、循环依赖或隐式全局状态。
- 状态所有者、生命周期和并发访问方式明确。
- 外部 SDK、数据库、网络和 UI 类型停留在适当边界。
- 错误在正确层级转换，没有被吞掉或无意义地层层透传。
- 测试验证公共行为和边界契约，而不是锁死内部实现。

实现发现设计不成立时：

- L0/L1：调整并简要说明；若新增边界风险，升级等级。
- L2：更新架构摘要，说明证据和取舍。
- L3：改变核心边界、公共契约或迁移策略时停止实施，重新确认。

## 完成前六类验收

### 1. 职责

- 每个新增或修改单元能用一句话描述“负责/不负责”。
- 不存在多个无关变化原因被方便性绑在一起。
- 没有继续向巨型函数、类型、文件或模块追加新职责。

### 2. 边界

- 选择了函数、类型、模块、package/crate 或服务中的最小有效层级。
- 公共 API 保持最小，内部实现和类型没有泄漏。
- 拆分收紧了可见性、依赖或状态，而不只是移动代码。

### 3. 依赖与数据流

- 依赖方向符合设计，没有循环、跨层捷径和服务定位器式隐藏依赖。
- 状态有唯一明确所有者，跨边界数据和控制流可解释。
- 需要独立演进或测试的核心规则没有被具体 UI、存储或第三方协议污染；简单固定流程没有为此强造抽象层。
- 错误语义与处理责任在边界处清晰。

### 4. 扩展性

- 已知的近期变化能局部完成，不需要修改大量无关单元。
- 每个扩展点至少对应一个真实变化或替换需求。
- 没有为假想需求引入额外层次、模式或服务。

### 5. 可测试性

- 核心规则能独立验证。
- 边界可用真实轻量实现、替身或契约测试隔离。
- 测试覆盖关键状态转换、错误路径和跨边界数据流。

### 6. 一致性

- 实现与已确认的 L2/L3 方案一致；偏离已有记录和理由。
- 模块入口、构建清单、公共文档和架构说明已按需同步。
- 无遗留旧接口、死代码、临时适配或重复实现。

## 工具验证

根据技术栈运行现有格式化、编译、测试和静态分析。若项目已有依赖图、循环依赖、未使用依赖或复杂度检查工具，一并运行；不要为了本次任务擅自引入整套工具链。

自动化只能暴露信号，不能代替职责判断。所有“通过”结论必须引用实际命令和结果。

## 完成报告

存在结构决策时使用：

```markdown
架构结果：
- 职责与边界：
- 关键依赖和状态流：
- 拆分或保留决定：
- 验证证据：
- 已知问题与后续建议：
```

没有架构变化时压缩为一两句话，不制造无价值报告。后续建议不得伪装成本次已完成内容。
