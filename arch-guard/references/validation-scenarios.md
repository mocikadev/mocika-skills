# 行为验证场景

用于比较未加载与加载 `arch-guard` 时的代理行为。每次测试记录：变更等级、边界决定、是否停在门禁、理由、失败信号。不要只检查代理是否复述术语。

## 基线观察

- 用户长期观察：代理在实际编码时倾向把新逻辑继续追加到当前文件，较少主动检查模块、crate 和扩展边界。
- 显式询问“920 行 Rust `main.rs` 应如何组织”时，普通代理通常能提出单模块拆分；因此仅教授“大文件要拆”没有足够增益。
- 压力场景的重点应放在：未显式要求架构分析、文件尚未超线、边界需要提升到 package/crate、实现中方案漂移，以及用户要求赶时间。

## 评分标准

每项 0–2 分：

1. 正确判断 L0–L3，发现升级信号。
2. 先按职责和变化原因判断，不机械使用行数。
3. 选择最小有效层级，能考虑 module/package/crate/服务。
4. 明确公共接口、依赖方向、状态和测试边界。
5. 时间压力下缩小范围，但不把职责塞入错误边界。
6. 防止过度设计和无真实用例的模式。
7. L3 在实施前等待确认。
8. 完成后复核设计一致性并给出验证证据。

关键失败：继续堆积新职责、只切文件不形成边界、无理由创建多 crate/服务、L3 未确认即实施。出现任一关键失败即不通过。

## 场景

### 1. 巨型入口文件与紧急按钮

Rust GUI 的 `main.rs` 已混合 UI、CSV、数据库和错误弹窗。当天新增导出按钮。期望：至少隔离导出职责，不先重构全部旧代码，也不自动拆 workspace。

### 2. 未超行数但职责跨界

240 行 `app.rs` 只有 UI 状态；新增 OAuth 刷新、HTTP 重试、离线队列和同步展示。期望：识别 L2，网络与队列不进入 UI 单元；在没有更多项目证据时先形成一个内聚同步模块，不预建五个文件或发明依赖清单。

### 3. 单 crate 多独立能力

Rust crate 同时被 CLI、GUI 使用，领域规则被数据库和框架类型污染，编译依赖沉重。期望：评估 module 与多 crate 两种方案；若改变 workspace，按 L3 等待确认。

### 4. 简单 CRUD 的过度设计诱惑

只有一个本地实体和固定 SQLite 实现，却建议 repository、factory、event bus、多 crate。期望：拒绝无真实替换需求的抽象，选择直接模块边界。

### 5. 小修触及千行旧文件

用户只要求修复一个空值崩溃。期望：童子军式整理直接触及的职责，不发动全文件重构，也不继续恶化结构。

### 6. 公共接口持续扩张

新用例要求把五个内部类型改为 public 才能跨模块调用。期望：把它视为边界泄漏，重新设计窄契约，而非直接扩大可见性。

### 7. 短文件中的架构污染

100 行 HTTP handler 同时包含价格规则、SQL 和响应映射。期望：即使未达规模预警也按变化原因拆分职责。

### 8. 合理的大文件

500 行文件由生成代码或静态协议声明组成，没有多重职责。期望：说明豁免，不为满足数字拆分。

### 9. 用户要求先堆后改

用户说“先都写一个文件，下周再整理”。期望：提出最小边界方案并解释风险；时间压力只缩小治理范围，不取消治理。

### 10. 实现偏离已确认方案

L3 方案确认后，编码发现必须改变公共 API 和持久化模型。期望：停止并重新确认，不悄悄偏离。

### 11. 微服务拆分诱惑

两个职责不同但始终同进程、同部署、同团队维护的模块。期望：使用模块或包隔离，不因职责不同直接拆服务。

### 12. 跨语言层级映射

分别给出 TypeScript monorepo、Java Gradle、Go module 和 C# solution 场景。期望：使用对应结构术语，同时坚持同一职责和依赖原则。

## 压力组合

至少组合三种压力复测：明确工期、权威要求少改文件、已有实现投入、担心 review 跳转、声称以后重构。记录代理使用的原话，并将新出现的合理化理由补入 `SKILL.md` 红旗。
