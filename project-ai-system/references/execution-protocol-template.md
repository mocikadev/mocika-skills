# AI 执行协议模板

生成或修订模式使用。目标是规定 AI 在本项目内如何接任务、澄清、设计、实现、验证和汇报。

## 输出路径

默认建议：`docs/ai/execution-protocol.md`

入口文件只保留摘要和链接，不粘贴完整协议。

## 模板

```markdown
# AI 执行协议

## 适用范围

本协议规定 AI 代理在本项目中处理需求、实现变更、修复缺陷、整理文档和发布交付时的最低执行标准。

## 任务分级

| 等级 | 判断标准 | 最低流程 |
|------|----------|----------|
| 小改动 | 文案、注释、局部配置、无行为变化 | 直接修改 + 验证 |
| 普通变更 | 单模块功能或行为变化 | 澄清需求 + 简短设计 + 实现 + 验证 |
| 复杂变更 | 多模块、架构、数据流、UI 流程或外部接口变化 | spec + 设计/计划 + 分阶段实现 + 回归验证 |
| 高风险变更 | 数据删除、迁移、权限、安全、发布、不可逆操作 | 影响说明 + 用户确认 + 执行计划 + 验证证据 |

## 开始或恢复任务

每次开始或恢复任务时，先检查当前工件状态：

- 是否已有 spec 或需求说明
- 是否已有设计/计划
- 是否已有执行契约或任务清单
- 是否存在未完成验证、未处理 review 或中断进度

状态不一致时，先修复工件状态，不直接继续实现。

## 新需求流程

1. 需求不清时，先补齐 `docs/requirements/project-spec.md`
2. 明确目标、范围、非目标、约束和验收标准
3. 普通及复杂变更必须先说明实现方案，再修改代码
4. 若用户中途变更目标，先更新 spec/计划，再继续执行

## 执行契约

复杂变更进入实现前，建议生成变更级执行契约，例如 `docs/ai/changes/<change-name>/execution-contract.md`。

契约至少包含：

- Intent Lock：本次变更的目标和非目标
- Approved Behavior：已确认的行为变化和验收标准
- Design Constraints：架构、接口、数据、兼容性约束
- Task Batches：可分批验证的任务清单
- Test Obligations：必须新增或运行的测试
- Review Gates：每批完成后的审查点

没有执行契约或契约已过时时，不进入复杂变更实现阶段。

## Bug 修复流程

1. 先复现或确认症状，不直接猜测修复
2. 定位根因，说明影响范围
3. 添加或更新回归验证方式
4. 修复后运行对应验证命令

## 实现约束

- 优先遵循现有代码结构、命名和工具链
- 不做与当前任务无关的重构
- 不引入新依赖，除非说明理由并获得确认
- 涉及共享格式、生成物、锁文件或跨文件协议时，同步更新所有相关文件

## 测试与 TDD

- 涉及行为变化时，先定义可验证的期望结果
- 复杂逻辑、核心业务规则和 bug 修复优先测试先行
- 如果无法自动化测试，必须写明人工验收步骤
- 不为追求覆盖率编写只验证实现细节的脆弱测试

## 快速路径

轻量任务可跳过完整 spec/契约，但不能跳过验证：

- Hotfix：通常 ≤2 个文件，修复明确缺陷，不引入新模块或新行为范围
- Tweak：通常 ≤4 个文件，限文档、配置、样式或注释等低风险修改
- 超出轻量边界时，升级为普通或复杂变更流程

必须升级的情况：

- 用户目标、成功标准或验收方式不清
- 跨模块、跨平台、跨服务或影响公共 API
- 修改数据结构、存储格式、权限、安全或兼容性
- 引入新依赖、迁移、发布流程或不可逆操作
- 需要新增能力，而不是修正已确认的小问题
- 验证方式无法用现有命令或简单人工步骤覆盖

## 验证与完成声明

完成前必须给出新鲜验证证据：

```bash
{项目测试命令}
{项目构建或检查命令}
```

汇报时说明：

- 修改了什么
- 如何验证
- 未验证或仍有风险的部分

不得在未验证时声称“完成”“修复”“通过”。

## 收口与同步

变更完成后检查是否需要同步文档：

- 行为变化 → 更新 spec 或需求文档
- 架构/接口变化 → 更新设计文档
- 验证方式变化 → 更新质量或执行协议
- 实际实现偏离计划 → 记录 delta，并在收口时合并回主文档

## 风险操作

执行以下操作前必须请求用户确认：

- 删除数据、重置历史、覆盖用户改动
- 数据迁移、权限/安全策略变更
- 发布、部署、推送到远端
- 大范围格式化或批量重命名

## 与全局规则的关系

- 全局代理规则继续生效
- 本协议只记录本项目额外要求或覆盖规则
- 若冲突，先向用户说明冲突点并请求裁决
```

## 审计要点

- 是否定义任务分级
- 是否要求开始/恢复任务时检查工件状态
- 是否要求需求不清时先补 spec
- 是否定义复杂变更的执行契约
- 是否定义 hotfix/tweak 快速路径
- 是否定义轻量任务升级条件
- 是否定义 bug 修复流程
- 是否定义测试/TDD 门槛
- 是否要求完成前验证
- 是否要求收口同步，防止 spec 腐烂
- 是否列出项目特有风险操作
- 是否说明与全局规则的关系
