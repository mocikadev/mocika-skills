# 项目 Spec 模板

启动模式使用。目标是把“想做什么”澄清成 AI 可执行、可验收的项目说明。

## 澄清顺序

信息不足时按优先级提问，最多一次问 3 个问题：

1. **目标**：项目要解决什么问题？目标用户是谁？
2. **成功标准**：什么结果说明项目达成目标？
3. **范围**：本阶段包含什么？明确不包含什么？
4. **约束**：技术栈、平台、时间、兼容性、安全、性能、合规约束
5. **验收**：如何验证完成？人工验收、自动测试、演示流程、性能指标
6. **交付物**：代码、文档、部署包、设计稿、API、数据迁移等

## 输出路径

默认建议：`docs/requirements/project-spec.md`

如项目已有 spec 目录或命名规范，沿用现有路径，不强行改名。

## 模板

```markdown
# {项目名} Project Spec

## 背景与目标

- 背景：{为什么要做}
- 目标用户：{谁会使用或受影响}
- 目标：{达成什么结果}

## 成功标准

- {可观察的业务/用户结果}
- {可验证的质量或性能结果}
- {交付完成的判断标准}

## 范围

### 本阶段包含

- {功能/模块/流程}

### 本阶段不包含

- {明确排除项，避免 AI 自行扩展}

## 用户场景

1. {角色} 在 {场景} 下，需要 {能力}，以便 {收益}。

## 关键约束

- 技术约束：{语言、框架、平台、版本}
- 质量约束：{测试、性能、安全、兼容性}
- 协作约束：{评审、发布、权限、审批}

## 验收标准

- [ ] {可执行验收项}
- [ ] {自动化验证命令或人工检查步骤}

## 风险与待确认

- 风险：{已知风险与影响}
- 待确认：{未决问题，必须在实现前确认}
```

## 规则

- 不编造用户未确认的业务目标、截止时间或合规要求
- 不把实现方案写成需求；实现方案放 `docs/design/`
- 验收标准必须可验证，避免“体验良好”“性能优秀”等空泛表述
