# Project Skill 边界规则

生成、修订、审计模式使用。目标是判断内容应放入口文件、docs，还是拆成 project skill。

## 放入口文件

只放 AI 开始工作前必须立即知道的高价值信息：

- 项目状态、技术栈、关键命令
- 执行协议摘要和链接
- 关键约束、跨文件同步要求、特殊路径
- docs 和 project skills 导航

## 放 docs

适合长期参考、需要展开阅读、但不需要每次激活流程的内容：

- 需求、spec、设计、架构说明
- 风格规范、测试策略、发布流程
- 背景资料、决策记录、故障复盘
- 大段表格、完整枚举、静态清单

## 做成 project skill

满足以下任一条件时建议做 skill：

- 多步骤操作会重复执行，且顺序重要
- 需要 AI 主动判断何时触发
- 涉及项目专属术语、业务规则或上下文
- 需要调用脚本、模板、检查清单或固定输出格式
- 错误执行会造成明显返工、风险或规范漂移

典型例子：

- 发布流程、复杂回归验证、数据迁移
- 项目专属代码生成、接口变更流程
- 设计评审、性能分析、事故复盘

## 不要做成 skill

- 一次性说明或历史记录
- 单纯目录索引
- 可由格式化器、lint、CI 自动保证的机械规则
- 太泛化、与项目无关的通用代理规则

## 输出格式

建议 project skill 清单使用：

| Skill | 触发场景 | 放置路径 | 原因 |
|-------|----------|----------|------|
| `{skill-name}` | {何时使用} | `{path}` | {为什么不是 docs/入口文件} |
